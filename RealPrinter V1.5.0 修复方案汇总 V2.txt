V2-1 🔴【新增·最高优先】拖动延迟保护被 cfg 绑死，关掉 DragToUse 反而回到崩溃窗口
═══════════════════════════════════════════════════════════════════
【问题定位】RealPrinterMod.MachineBuilder.cs · OnTargetItemFunc() L457~487
现码：
    if (Config.DragToUse && IsDraggingNow())
    {
        QueueDrop(target);
        return;
    }
    RunTargetItemFunc(target);

【依据（全部可确证，不需实机）】
① 这段"压后一帧"**不是功能，是安全机制**。文件自己的注释 L459~477 写得很清楚：
   游戏在 `ItemMouseDragHandler.EndDrag` 内部**自己**调 `GameItem.Target`
   （崩栈：`Patch_Target.Prefix ← managed_EndDrag → OnTargetItemFunc`），
   此刻 target 可能正在被销毁；此时进 IL2CPP（OpenEditor → DetectFeatures）
   = 野指针喂原生函数，**AccessViolationException 抓不住**（MEMORY 铁律）。
   延迟到"EndDrag 已跑完、状态已稳定"的下一帧，才把窗口从最危险的时刻挪走。
② 但这段保护的**前置条件写成了 `Config.DragToUse`**：面板一关，保护整条消失，
   拖动落点的 Target 调用直接落到 `RunTargetItemFunc(target)` → OpenEditor
   → `DetectFeatures(target)`（编辑窗准入里只有 IsSafeTarget 一道活体闸，
   而注释 L388~399 自己承认 WasCollected 未必及时置位 → 拦不住半死对象）。
③ 而 README「常见问题」恰好教玩家：**"拖动机器会闪退 → 先把 DragToUse 关掉"**。
   → 在 V1.5.0 里，这个自救动作把玩家直接推回 V1.5.0 想修掉的那个崩溃窗口。
   （V1.4.x 时代没有这个问题：那时首行是**无条件**的 `if (IsDraggingNow()) return;`，
     cfg 关不关都短路。是 V1.5.0 把短路挪进 cfg 条件后才出现的。）
④ 同一处的注释 L479 写「cfg 关掉就退回 V1.4.x 行为：拖动不触发」——**与代码不符**。
   代码的实际行为是"既触发、又不延迟"，三者（注释/README/代码）互相矛盾。

【修复】把"延迟"与"触发开关"拆开：延迟永远生效，cfg 只决定落点要不要开窗。
方案 A（推荐，改结构，不依赖任何状态判得准不准）：
    // ★ 拖动状态在代码里从来没有"判得准"的时候（采样一帧一次、EndDrag 时序不定），
    //   所以安全做法是**结构性的**：一律压后一帧再决定。
    internal static void OnTargetItemFunc(GameItem target)
    {
        // 无条件入队。点击路径同样只晚一帧（≈16ms，玩家无感），
        // 但换来的好处是：**开窗这件事永远不会发生在 EndDrag 内部** ——
        // 不依赖缓存准不准、不依赖实时读得到什么、不依赖游戏哪个版本先置 false。
        QueueDrop(target);
    }

    private sealed class PendingDrop
    {
        public GameItem Target;
        public IntPtr Ptr;
        public float QueuedAt;
        public bool FromDrag;      // ★ 新增：本次落点是不是拖动来的
    }

    private static void QueueDrop(GameItem target)
    {
        if (target == null) return;
        IntPtr p;
        try { p = ((Il2CppObjectBase)target).Pointer; } catch { return; }
        if (p == IntPtr.Zero) return;
        _pendingDrop = new PendingDrop
        {
            Target = target,
            Ptr = p,
            QueuedAt = Time.unscaledTime,
            // 尽力而为的归类（判错的最坏后果只是"关着拖动时多开一次窗"，不是崩溃）
            FromDrag = IsDraggingNow() || IsReallyDraggingNow(),
        };
    }

    private static void TickPendingDrop()
    {
        var pd = _pendingDrop;
        if (pd == null) return;

        // ① 拖动触发关着 → 拖动落点直接丢弃（回到 V1.4.x「拖动不触发」）
        if (pd.FromDrag && !Config.DragToUse)
        {
            _pendingDrop = null;
            return;
        }

        // ② 拖动还没结束 → 继续等（含 2 秒超时保护，原逻辑不动）
        if (IsDraggingNow())
        {
            if (Time.unscaledTime - pd.QueuedAt < 2f) return;
            _pendingDrop = null;
            RLog.Detail("拖动落点等待超时（isDragging 未复位），已丢弃本次落点。");
            return;
        }

        // ③ 真正开窗（指针漂移闸 / 活体闸保留原样）
        _pendingDrop = null;
        ...（其后代码不变）

【为什么不选方案 B（V1 那条"cache || 实时读"）】
  实时读只能证明"此刻 isDragging 是 false"，**证明不了"EndDrag 已经跑完"** ——
  危险窗口恰恰就是"isDragging 已 false、EndDrag 还没跑完"那一小段。
  也就是说 B 在最需要它的时候恰好给不出保护，而 A 从结构上让这段窗口不可能被踩到。
  （`IsReallyDraggingNow()` 仍然保留，只用于 QueueDrop 的 FromDrag 归类。）

【验证】
· 面板**关掉** DragToUse：反复拖打印机 10 次 → 一次不开窗、一次不闪退
· 打开 DragToUse：拖到商品上 → 松手后开窗（不早不晚）
· 装备后左键点商品 → 开窗（晚一帧，玩家无感）
· 拖动穿过工具箱/档案箱 → 仍然进得去（让路机制不受影响）
· README 那句"关掉 DragToUse 自救"在新版下必须仍然成立，且要补一句说明

V2-2 ⚠️【V1-修复1 修正】拖动起始帧的实时兜底 —— 前提未取证，降级为加固项
═══════════════════════════════════════════════════════════════════
【V1 的说法】"按下鼠标、移动超过拖动阈值、游戏同一帧内调 GameItem.Target 时，
  缓存里 _dragging 还是 false → 立刻开窗"。

【核对结论】现象方向成立，但**前提没有证据**：
· `GameItem.Target` 的调用点只有两处（依据：课题文档《共享机制与 mod 实战》§6 +
  实机崩栈 `<EndDrag>d__12.MoveNext()`）：① 装备后点击；② `EndDrag` 异步状态机。
· 拖动过程中游戏问的是 `MayTarget`/`CanTarget`（高亮），**不是 Target**。
  MachineBuilder.cs L511 那句"悬停高亮也会问 Target"是推断，未取证。
· 所以"同一帧内调 Target"这个前提，我找不到支撑。**未验证**。
【但它值得加】缓存滞后一帧是真的，代价也确实低：
  `IsDraggingNow() || IsReallyDraggingNow()` 的 `||` 会短路 —— 缓存为 true 时
  不多读；只有"缓存说没在拖"（点击路径 + 起步帧）才多两次 IL2CPP 属性读。
【V2 定级】从 V1 的"立即"降为 P2 加固项。**理由**：V2-1 的方案 A 已经从结构上
  让"起步帧误开窗"失效（起步帧的落点同样进队列、同样等拖动结束才处理），
  这条只剩"多一道判据"的意义。
【代码】`IsReallyDraggingNow()` 保留 V1 写法（finally 兜底 + RLog.Swallowed），
  调用点改到 QueueDrop（见 V2-1），不再放在 OnTargetItemFunc 第一行。
【验证】连拖 10 次 0 次误开窗；点 10 次每次开窗。

V2-3 ⚠️【V1-修复2 修正】容器判据缓存 —— 单槽缓存等于没缓存
═══════════════════════════════════════════════════════════════════
【V1 的判断】"拖动期间落点是唯一的（_pendingDrop 只有一个），所以单槽足够"。
【核对结论】这个论证**用错了量**：
· 单槽缓存的服务对象不是 `QueueDrop`（落点确实唯一），而是 `IsTargetEditable`；
· `IsTargetEditable` 挂在 `MayTarget`/`CanTarget` 上，游戏**每帧对可见的每个物品
  都问一遍**（依据：Interact.cs L113~117 / L190~196 记录的实机日志"每秒被调 900+ 次，
  单次尝试刷出 900+ 行"）；
· 拖动中每帧被问的目标是**一整排不同物品**（N 个），指针键每帧都被下一个物品顶掉：
  N 个物品 × 每帧重算 → **一次都没省**。V1 的缓存收益 ≈ 0。

【修复】拖动期按指针**多槽缓存**（容器 tag 在一次拖动里不会变），拖动结束清空：
    private static readonly Dictionary<long, bool> _containerCache = new Dictionary<long, bool>();
    private static bool _draggingPrev;

    private static void SampleDragState()
    {
        try
        {
            var h = ItemMouseDragHandler.current;
            _dragging = h != null && h.IsDraggingItem;

            // ★ 拖动结束的下降沿 → 清缓存（见下"清缓存位置"）
            if (_draggingPrev && !_dragging) _containerCache.Clear();
            _draggingPrev = _dragging;
        }
        catch (Exception ex) { RLog.Swallowed("SampleDragState", ex); _dragging = false; }
    }

    private static bool IsContainerLikeCached(GameItem target)
    {
        long p;
        try { p = ((Il2CppObjectBase)target).Pointer.ToInt64(); } catch { return false; }
        if (p == 0) return false;

        bool v;
        if (_containerCache.TryGetValue(p, out v)) return v;

        if (_containerCache.Count >= 512) _containerCache.Clear();   // 上限保护
        try { v = target.IsTag(ContainerTag); }
        catch (Exception ex) { RLog.Swallowed("IsContainerLike", ex); v = false; }
        _containerCache[p] = v;
        return v;
    }

★ 清缓存的**位置**是 V1 写错的地方：V1 说"在 TickPendingDrop 处理完后清"，
  但 TickPendingDrop 在 `_pendingDrop == null` 时**首行就 return** ——
  而"拖动中让路给箱子"这条路恰恰不会产生落点 → 缓存永远不清：
  两次拖动之间指针被复用就会留下错误结论，而且会无界增长。
  必须放在**每帧都会跑的 SampleDragState 的下降沿**。

【收益量级】拖动中每物品每帧：1 次 IL2CPP 调用 → 1 次字典命中
  （与同一路径上 HotLog 的开销同量级，可接受）。
【验证】柜台塞满 20+ 件时拖动穿过，帧率与 V1.5.0 无差别；
  拖进工具箱/档案箱仍然进得去；拖到商品上仍然开窗。
【残留风险（如实记）】让路判据本身仍用的是**采样缓存**（IsTargetEditable 热路径，
  不能实时读）。理论上"松手那一帧采样还没跟上"会让让路失败 → 表现为"箱子放不进"。
  实测（README：拖进箱子可用）说明概率极低；若实机复现，再考虑把它换成
  "拖动闩锁"（本帧或上帧拖过就算在拖）。**不作为本轮改动**。

V2-4 ⚠️【V1-修复3 部分否决】主仓库 tag —— 取证保留，兜底代码不能上
═══════════════════════════════════════════════════════════════════
【V1 要验证的问题本身是对的】IsContainerLike 只查 ContainerTag；
  若"主仓库里的物品"不带这个 tag，拖到它身上会被我们接管 → 开窗，而不是被收纳。
【但 V1 给的第二步（ContainsPtr 兜底）有两个硬伤，**否决**】
① **会误伤前柜台 —— 直接废掉本机主用法**。兜底把"目标在 emp.frontInvinvElement 里"
   也算容器 → 玩家把打印机拖到**柜台上的香烟**（README 头条用法）会被判成"容器"
   → 让路 → 开不了窗。
   依据：RealPrinterMod.DealerSupply.cs L27~35，`TryGetInventory(true)` 返回的就是
   前柜台 `frontInvinvElement`。V1 的兜底里那句"前柜台"是照抄了工具函数，
   没意识到柜台正是主战场。
② **复杂度放错地方**。`IsTargetEditable` 在 900+/s 的热路径上，
   ContainsPtr 是 O(N) 的 IL2CPP 列表读 → 比一次 IsTag 贵 N 倍，还得再配一套缓存。
③ 而且它**没有回答真正的问题**：判据仍然是"目标物品是不是容器"，
   而不是"**落点所在的库存是不是储物类**"。两者只在"目标恰好是个箱子"时才等价。

【V2 做法】只做第一步取证，且把日志放在**冷路径**（每次拖动 1~几次，不进热路径）：
    // QueueDrop 里追加（VerboseLog 控制）
    if (Config.VerboseLog)
        RLog.Detail("拖动落点: id=" + SafeId(target)
                    + " 目标带ContainerTag=" + IsContainerLike(target)     // 目标自己是不是容器
                    + " 在柜台=" + IsOnFrontCounter(target)                 // 已有函数 DealerSupply.cs
                    + " 在主仓库=" + IsInWarehouse(target));                // 新写一个同构的（照抄 IsOnFrontCounter）
    实机跑三种落点，连"游戏实际做了什么"一起记：
      a. 拖到主仓库的**空格子**  → 预期：放进去（走放置逻辑）
      b. 拖到主仓库里**已有的商品**（香烟等）→ 看：开窗？还是被收纳？← **这一条决定要不要改**
      c. 拖到**柜台上的商品**    → 必须：开窗 ← **红线，任何方案都不能破坏**
   判定：只有 b 出现"本想收纳却被开窗"才算缺陷。
   若确认是缺陷，优先考虑"按落点所在库存判让路"（即上面 ③ 的那套判据），
   而不是按目标物品的 tag —— 后者必然要在"柜台里的商品"和"仓库里的商品"之间二选一。
【未验证清单】
  · 主仓库 / 柜台物品是否带 CONTAINER_TAG（本条的未知量）
  · 玩家拖到"库存里的商品"上时，游戏的落点优先级（放置 vs 使用）

V2-5 ⚠️【V1-修复4 采纳 + 补根因】许可自检分级 —— 分级治不了"为什么会降级"
═══════════════════════════════════════════════════════════════════
【V1 诊断成立】Core.cs L819~824 把"类别中文名没解析全"塞进 `bad` →
  RealPrinterMod.cs L69~77 打成 `RLog.Error`（MelonLoader 红字，每次启动一条）
  → 玩家以为 mod 坏了。拆 `(functional, cosmetic)` 两级、cosmetic 走 Warning：
  **采纳，照 V1 代码改**。

【只改这里不够 —— 根因在 ResolveCategoryNames（Core.cs L715~757）】
    if (_catRealNames.Count > 0)
    {
        _catResolved = true;      // ← 只要读到 ≥1 条就**永久锁定**
        ...
        return true;
    }
    ...
    if (_catRetry < 3) { _catRetry++; ... return false; }   // ← 只有"一条都没读到"才计数
· 16 张表只要在那个时刻有 1 张已 .cctor 完、其余还没 → 表被固化成"1/16"；
· 而 `_catRetry` 只在**零条**时才递增 → **部分解析永远不会重试**；
· 于是 cosmetic 那条"只解析出 x/16"会**每次启动都刷**。
  分级只把它从红字变成黄字，噪音没消失。

【V2 一起做（四处）】
① 返回值分级：`SelfCheckLicense(out List<string> functional, out List<string> cosmetic)`，
   调用点 functional → RLog.Error，cosmetic → RLog.Warning。
② 判定"完整解析"= `_catRealNames.Count == _catListAccessors.Count`；
   只有完整解析才 `_catResolved = true`；部分解析与零条**走同一条重试路径**
   （仍受 `_catRetry < 3` 约束，不会无限重试，也不会每次开窗刷异常）。
③ cosmetic 里**列名字**，不只报数量：
   "类别中文名未解析：模块卡死 / 赠品（界面会显示 CATEGORY_ 英文原名，功能不受影响）"
   —— 比"3/16"可定位得多（这正是"静默失效要留证据"的同一条纪律）。
④ `_catRetry` 语义写清：从"零条才计数"改成"未完整解析就计数"，并把注释里的
   "读不到"改成"未读全"，否则下一个人又会按旧语义改回去。
【验证】正常启动只有一行 Detail；人为把某张静态表读成空 → 启动出现
  **一行** Warning 且带缺失类别名，不是 Error、不重复刷。
